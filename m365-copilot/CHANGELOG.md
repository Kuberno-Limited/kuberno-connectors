# Changelog

## 1.6.0
- Declare `search_documents`, across `functions`, `run_for_functions` and the `mcp_tool_description` snapshot. It searches the documents held in the Kube instance by their metadata — file name, title, description, document type, file type, size and the effective, uploaded and modified date ranges — optionally scoped to one entity, officer, external party, committee or registration, and returns the page's documents with the record each is filed against. It reads no document content and honours the caller's own document permissions, so a document the user cannot open in Kube is not returned here either.

- Declare `search_documents_ai`, across `functions`, `run_for_functions` and the `mcp_tool_description` snapshot. Unlike `search_documents` it matches what is written INSIDE each document, by meaning or by literal wording, and returns the passages that matched alongside the metadata. It is only usable where the Kube instance has AI capability enabled — the server hides it from `tools/list` and refuses the call otherwise — but the published manifest is static, so a tenant with AI off still sees it advertised. Its `TotalItems` is approximate and its paging is bounded, which its description now says rather than inheriting the exhaustive-paging guidance the metadata tools carry.

- Declare `get_document_summary`, across `functions`, `run_for_functions` and the `mcp_tool_description` snapshot. It reads the system-generated summary Kube already holds for one document, by its DocumentId from `search_documents` or `search_documents_ai`; it never generates one. A document with no stored summary answers with guidance for producing one client-side rather than an error, and every summary carries the AI-generated-results disclaimer. Only usable where the Kube instance has both AI capability and document summarisation enabled — the same static-manifest caveat as `search_documents_ai` applies.

- Declare `get_document`, across `functions`, `run_for_functions` and the `mcp_tool_description` snapshot. It retrieves one or more documents by DocumentId from `search_documents` or `search_documents_ai`, server-side filtered to documents the signed-in user can see. How a document comes back is configured by the organisation rather than chosen per call: streamed extracted text, paged for a long document; a deep link back into Kube that re-checks the user's own permissions when opened; or no document access at all, in which case searching and summarising are unaffected.

## 1.5.0
- The declarative agent's `instructions` now cover tenancy: which tenant the connector is on is not derivable from entity or officer data, so a question about it has to reach `get_mcp_session`, and the switch link the tool returns has to be handed to the user rather than described as available. Both directions previously existed only in `McpGatewaySwitchContext.InstructionsNote`, which the server appends to the initialize instructions for a gateway-fronted session — and M365 Copilot never performs initialize, so it received the session protocol's other half and nothing about tenants. Unlike `McpServerInstructions.SessionProtocol` the note cannot be repeated word for word, because it is built per session from the live tenant slug and that connector's own `/sessions` URL; this is a static equivalent, pinned by a test.
- `description_for_model` now mentions the tenant the connector operates against and where the user switches it. Copilot routes over `functions[]` only once a query looks like it belongs to this plugin, and "which tenant are you connected to" carries no entity or officer signal to get it there — which is why the 1.4.0 change to that array, correct in itself, did not make the question reach the tool.

## 1.4.0
- `functions` now carries each tool's opening paragraph from the server rather than a separate, shorter summary written by hand. Microsoft 365 Copilot routes from that array, and the summaries said only what each tool returned — none of them carried the server's guidance on when to call it, so a question a tool description names explicitly, such as which tenant the connector is operating against, did not reliably reach `get_mcp_session`. The full descriptions stay in the `mcp_tool_description` snapshot, which is read once a tool has been chosen; carrying them in both places would add 78KB of prose to every routing decision. Both sites are now generated from the server and pinned by tests, so neither can drift again.
- The pinned `mcp_tool_description` snapshot now carries each tool's `annotations`, including `readOnlyHint`. Microsoft 365 Copilot asks the user to confirm every tool call unless the tool declares that hint, and a pinned snapshot is the only `tools/list` an M365 client ever sees — so although the server has always emitted the hint, every read-only search and lookup still prompted. The values are taken from each tool rather than assumed, so a writing tool declared here would publish its own. `title` travels with them, which the Anthropic Connectors Directory requires alongside the hints.

## 1.3.0
- Declare `get_mcp_session`, across `functions`, `run_for_functions` and the `mcp_tool_description` snapshot. It reports which Kube tenant the connector is currently operating against, the connecting client's name, and, for a user who can reach more than one tenant, the gateway page where they can switch this connector to another tenant. The switch takes effect on the next tool call without reconnecting the agent. A user with access to one tenant sees the tenant name and that switching is unavailable. The tool takes no parameters and reads nothing from Kube data.

## 1.2.0
- Every filter parameter on the paged tools now accepts a list of values instead of a single one, so one call can ask for several registrars, jurisdictions, entity types or appointment types at once. Values within a parameter are combined with OR and different parameters with AND, matching the multi-select filters on the corresponding Kube screens. This changes the published schema of the filter parameters that previously took a single string, so a caller that still sends a bare string where a list is now declared no longer matches the schema.
- Widen the filter sets on the tools whose Kube screen offers a full filter panel, so each accepts what that screen accepts. Entity search adds registrar status, company status, responsible owner, tags, audit status, client name and client number. Registrations add name, registration number, registrar, country, jurisdiction, registration type, registrar status, registration status and a registered-from/registered-to date range. Activities add team, party, overdue state, filing reference, filing-prepared and filing-submitted date ranges, and the option to exclude the entity's registrations rather than always spanning them. Date-range filters are day-granular: a bound is read as a whole day, so an end-of-day cutoff cannot be expressed and each description says so rather than silently narrowing the window.
- Add a free-text `query` filter to the entity and officer record tools — appointments, compliance dates, roles, contacts, addresses, alternates, user defined fields, meetings, committees and external appointments. Each searches the same columns as the keyword box on the corresponding Kube tab, and because those tabs differ from one another so do the columns, which each tool's description sets out. Words are combined with AND, so every word must match somewhere in the searched columns. The user-defined-field tools search per scope: a Field row matches its own name and description, a Group row matches the group's name and description, and a List row matches neither, because only the cell's rendered value is searchable there and that cannot be resolved without the application.
- Declare `get_my_activities`, which lists the signed-in user's own activity workload with filters for team, party, category, type, jurisdiction, status, filing reference, several date ranges and open/overdue/complete state. The MCP server has served this tool for some time, but it was absent from `functions`, `run_for_functions` and the snapshot, so Copilot could not route to it however the user phrased the question. `description_for_model` now mentions the workload owned by the signed-in user or their teams, so a question about a team's outstanding work reaches this tool rather than the per-entity activities one.
- Correct a parameter name that has been wrong since activities were first declared. This manifest published a boolean `complete` on `get_entity_activities`, while the server has only ever accepted `isComplete`. A Copilot caller passing `complete` was therefore ignored in silence — no error, just unfiltered results, so a request for outstanding activities returned completed ones too. The parameter is now `isComplete` and the filter takes effect, which is a change in behaviour for anyone who was unknowingly relying on the unfiltered result.
- Re-take the `mcp_tool_description` snapshot from the server's current `tools/list`, which brought twenty-three of the declared tools back into step: mostly reworded descriptions, plus the filter parameters and array types above. Several descriptions now also steer a caller to omit the active-only filter unless the user explicitly asks about inactive records, and to fetch the field catalogues once and reuse them rather than per question. The snapshot is now compared against the server automatically, so this class of drift fails a check instead of shipping.

## 1.1.0
- Expand the declared toolset from 12 functions to 25 — added the entity contacts, addresses, meetings, registrations, activities, alternates and user-defined-field tools, and the officer contacts, addresses, alternates, external appointments, committees and user-defined-field tools — across `functions`, `run_for_functions` and the `mcp_tool_description` snapshot. The 12 pre-existing snapshot entries were re-taken from the server's current `tools/list` rather than carried over: all 12 had drifted; one (`get_entity_appointments`) was also missing input-schema parameters the server accepts, and one (`search_parties`) carried a stale parameter description.
- Bring the agent's own descriptions up to the same toolset: `description_for_model` (which Copilot uses to decide whether to route a query here) and the declarative agent's `instructions` now cover contacts, addresses, meetings, registrations, activities, alternates, committees, external appointments and user defined fields rather than only the original five subject areas, and the human-facing descriptions match. The `instructions` no longer tell the agent to read an empty result as the user lacking access — an empty result equally means nothing is recorded, so it establishes nothing either way.
- Re-take the `mcp_tool_description` snapshot for thirteen tools whose wording was corrected on the server, so no tool description now contradicts the `instructions` above. `get_entity_dates`, `get_entity_contacts`, `get_entity_addresses`, `get_entity_activities`, `get_officer_contacts` and `get_officer_addresses` said only that an empty page means the caller lacks a permission, and now also say it happens when nothing is recorded, as the other section tools already did. `get_entity_registrations` and `get_entity_activities` no longer claim an `R|` registration ref is rejected by "any other tool" — only `get_entity` is named, which is the tool that rejects it. `get_entity_registrations` no longer asks the agent to read `Status` and `RegisteredOfficeAddress` as one of two things according to `CompanyRegistered`, which is null wherever the company- and tax-registration capability is off. And six descriptions no longer name `fetch` as an unavailable follow-up, since it is not one of the 25 functions this manifest declares.
- Re-take the snapshot for `list_entity_fields` and `list_officer_fields` as well: on the server both now answer only a caller who can open the corresponding Kube screens, so their descriptions no longer say no permission filtering applies to the catalogue and instead say the call is refused by name without that role. The catalogue's contents are still unfiltered — the change is who may fetch it, not what it contains.
